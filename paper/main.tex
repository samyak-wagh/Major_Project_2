\begin{abstract}
General-purpose language models often answer operating-systems (OS) questions fluently but without grounding in a course textbook, which is a problem for tutoring. We describe OS~Tutor, a retrieval-augmented generation (RAG) system over a standard OS textbook that can run with either a locally hosted, LoRA-fine-tuned Qwen2.5-1.5B-Instruct model or a cloud-hosted open-weight model. We built a 762-example instruction dataset in the same prompt format used at inference, and fine-tuned the small model with QLoRA. We compare four configurations in a pilot study: cloud model only, fine-tuned model only, RAG with the cloud model, and RAG with the fine-tuned model, using RAGAS faithfulness, answer relevancy and context precision on five textbook questions with an LLM judge. In this pilot, RAG with the cloud model scored a mean faithfulness of 0.591 and RAG with the fine-tuned model 0.523; answer relevancy was 0.953 and 0.893, and context precision was identical (0.50) because both systems share one retriever. With only five questions the differences between the two RAG systems are not statistically distinguishable. The fine-tuned system runs offline, but at a mean latency of 84.8~s per answer on a CPU-only machine against 4.2~s for the cloud system. We also report three evaluation pitfalls we encountered (decoding penalties that suppress quoting, conversation memory leaking between systems, and judge rate limits), and we disclose partial overlap between our training data and the gold question bank. The results should be read as a pilot, not a benchmark.
\end{abstract}

\section{Introduction}
Students learning operating systems often turn to general-purpose chatbots. These systems answer fluently, but their answers are not tied to the course textbook, and they can contain errors that a novice cannot detect. Retrieval-augmented generation (RAG)~\cite{lewis2020rag} addresses this by supplying retrieved passages to the model. Parameter-efficient fine-tuning such as LoRA~\cite{hu2022lora} and QLoRA~\cite{dettmers2023qlora} makes it feasible to adapt a small model on modest hardware, which in turn allows a tutor to run locally and offline.

This paper asks a narrow question: \emph{how close can a small, locally run, LoRA-fine-tuned model with RAG come to the same pipeline using a larger cloud-hosted open-weight model, on textbook question answering?} We built the system, ran a four-way comparison, and report what we measured, including the limitations of the measurement.

Our contributions are:
\begin{enumerate}
  \item OS~Tutor, an end-to-end RAG tutor over an OS textbook with interchangeable local (fine-tuned Qwen2.5-1.5B) and cloud (Groq-hosted) generators sharing one retriever.
  \item A 762-example instruction dataset (702 train, 60 validation) in seven categories whose prompt format matches the inference-time RAG prompt, including 40 out-of-context refusal examples.
  \item A four-system pilot comparison (cloud only, fine-tuned only, RAG$+$cloud, RAG$+$fine-tuned) using RAGAS metrics, with per-question results and latency.
  \item A candid account of evaluation pitfalls we hit and a disclosure of train/test overlap, to help others avoid the same errors.
\end{enumerate}

\section{Related Work}
\textbf{RAG for question answering.} Lewis et al.~\cite{lewis2020rag} combine a parametric generator with a non-parametric retrieval index; surveys such as~\cite{gao2023ragsurvey} catalogue later retrieval, chunking and reranking variants. We use a simple dense-retrieval baseline and leave advanced retrieval to future work.

\textbf{Parameter-efficient fine-tuning.} LoRA~\cite{hu2022lora} trains low-rank updates to frozen weights, and QLoRA~\cite{dettmers2023qlora} does so on a 4-bit quantised base. We follow this recipe for a 1.5B base from the Qwen2.5 family~\cite{qwen25}.

\textbf{Evaluation of RAG and hallucination.} RAGAS~\cite{es2024ragas} defines reference-light metrics for faithfulness, answer relevancy and context quality using an LLM. LLM-as-a-judge methods~\cite{zheng2023judge} are convenient but have known biases, and hallucination in generated text is widely documented~\cite{ji2023hallucination}. We therefore treat judge scores as indicative and discuss judge bias explicitly.

\section{System Description}

\subsection{Knowledge Base and Retrieval}
The knowledge base is a single OS-textbook PDF (Silberschatz, Galvin and Gagne~\cite{galvin}) parsed with PyMuPDF and split into overlapping chunks of 1000 characters with a 200-character overlap, giving 4{,}330 chunks. Chunks are embedded with BAAI/bge-small-en-v1.5~\cite{xiao2023cpack} and stored in a Qdrant vector database. At query time the top three chunks above a similarity threshold of 0.55 are retrieved; the local-model prompt truncates each passage to 300 words. Both RAG systems use this same retriever.

\subsection{Generators}
\textbf{Local generator.} Qwen2.5-1.5B-Instruct~\cite{qwen25} with our LoRA adapter, run on CPU in 32-bit floating point. Decoding uses sampling with temperature 0.1, top-$p$ 0.85, a repetition penalty of 1.1 and at most 256 new tokens. The system prompt asks for short, textbook-grounded answers.

\textbf{Cloud generator.} An open-weight 20B-parameter model (\texttt{openai/gpt-oss-20b}~\cite{gptoss}) served through the Groq API, using the repository's own RAG prompt.

Fig.~\ref{fig:arch} shows the pipeline. In RAG mode the question is embedded, passages are retrieved and the prompt is built from passages and question; in no-RAG mode the passages are omitted. The generator is selected per request.

\subsection{QLoRA Fine-Tuning}
We fine-tuned Qwen2.5-1.5B-Instruct with Unsloth and TRL's supervised fine-tuning trainer on a single GPU, with the base loaded in 4-bit. LoRA used rank 16, $\alpha=32$, dropout 0.05, applied to all attention and MLP projections (q, k, v, o, gate, up, down). Minority categories (comparative, analytical, negative edge case, applied conceptual) were oversampled 3$\times$. Training used an effective batch size of 16 (2 $\times$ 8 accumulation), learning rate $2\times10^{-4}$ with cosine decay and 5\% warm-up, weight decay 0.01, 8-bit AdamW, maximum sequence length 1024 and 3 epochs (150 steps). Fig.~\ref{fig:loss} shows the loss: training loss falls from 1.87 to 0.23 while validation loss is 0.577, 0.496 and 0.515 at steps 50, 100 and 150. The validation loss rises slightly after step 100, and its gap to training loss suggests some overfitting; we deployed the final (step-150) adapter.

\section{Evaluation Methodology}

\subsection{Systems}
We compare four configurations: \textbf{S1} cloud model without retrieval; \textbf{S2} fine-tuned model without retrieval; \textbf{S3} RAG with the cloud model; \textbf{S4} RAG with the fine-tuned model.

\subsection{Questions}
Our gold bank has 32 textbook questions with reference answers across deadlocks, CPU scheduling, memory management, disk scheduling and numerical problems. \emph{This pilot evaluates only the first five questions, all on deadlocks}, because of compute and judge-token limits. All numbers below therefore describe five questions from one chapter.

\subsection{Metrics and Judge}
We use RAGAS~\cite{es2024ragas} v0.4.3: \emph{faithfulness} (are the answer's claims supported by the retrieved context), \emph{answer relevancy} (does the answer address the question) and \emph{LLM context precision with reference} (are relevant passages ranked highly). Faithfulness and context precision require retrieved context, so they are undefined for S1 and S2, and we report them as not applicable instead of zero. The judge is Qwen3.8-27B served through the Groq API, with BGE-small embeddings for answer relevancy. Because the judge belongs to the same model family as our fine-tuned generator, scores for S2 and S4 may be biased in their favour; we did not measure this.

\subsection{Protocol}
Each question is sent to all four systems with conversation memory cleared before and after every request, so answers depend only on the question (Section~\ref{sec:pitfalls} explains why). Raw answers are saved before judging. Three judge calls timed out and were re-scored individually from the saved answers with the same judge; no answers were regenerated.

\subsection{Train/Test Overlap Disclosure}
We compared the 32 gold questions with the 762 training and validation questions. Three gold questions appear verbatim in the training data (preemptive vs.\ non-preemptive scheduling, demand paging, thrashing), and several others have close paraphrases. None of these three is among the five evaluated here. However, two evaluated questions (the four necessary conditions for deadlock, and the definition of a safe state) have paraphrased counterparts in the training data. Any conclusions about the fine-tuned systems should be discounted accordingly; a clean split is required before a full evaluation.

\section{Discussion}

\textbf{Gap between S3 and S4.} S4 is lower than S3 by 0.068 on faithfulness and 0.060 on answer relevancy. With five questions and a per-question faithfulness standard deviation of about 0.37, this gap is well within noise, and S4 actually wins on one question. We therefore make no claim that either system is better. What the pilot supports is the weaker statement that the 1.5B model with RAG produced answers in the same range as the 20B cloud model on these five questions, at a very different latency.

\textbf{Effect of retrieval on the fine-tuned model.} Adding RAG to the fine-tuned model changed mean answer relevancy from 0.876 (S2) to 0.893 (S4), a difference of 0.017 that is not meaningful at this sample size. We have no faithfulness comparison because it is undefined without retrieved context.

\textbf{Retrieval is the shared bottleneck.} Context precision is 0.50 for both RAG systems, with two questions at 0.0. For the opening question, retrieval returned the textbook's introductory anecdote about trains at a crossing rather than the formal definition. Improving retrieval (hybrid search, reranking, chunking) should raise both RAG systems, so it is orthogonal to the generator choice.

\textbf{Answer length.} S4's answers are short (mean 483 characters) compared with S3's (1582). Shorter answers contain fewer claims that a judge must verify, which may help faithfulness, while longer answers may score better on relevancy; we did not control for length.

\textbf{Failure modes.} A small model can still add unsupported content. For the deadlock-definition question, the fine-tuned system described deadlock as ``essentially a race condition,'' which is incorrect, even though its faithfulness score on that question (0.71) was higher than the cloud RAG system's (0.33). Faithfulness measures support by the retrieved context, not correctness, so the two should not be conflated.

\subsection{Evaluation Pitfalls}
\label{sec:pitfalls}
We hit three problems that would have distorted the results, and we describe them because they are easy to overlook.

\emph{Decoding penalties.} Our first configuration used a repetition penalty of 1.4 and a 5-gram no-repeat constraint. In common inference libraries these apply to the prompt as well as to the output, so the model is effectively forbidden from quoting retrieved text. The fine-tuned RAG system then produced incoherent answers and low faithfulness (0.19 on a three-question run). Reducing the penalty to 1.1 and removing the n-gram constraint produced coherent answers.

\emph{Memory leakage.} The chains keep recent conversation turns and insert them into later prompts. During sequential evaluation, one system's answer to a question appeared in the next system's prompt, and the next system copied it verbatim. We now clear memory before and after every evaluation request.

\emph{Judge limits.} Judge token quotas caused many scores to be missing; we changed the judge, reduced judged metrics for systems without retrieval, saved answers before judging, and re-scored missing cells individually.

The earlier three-question run is \emph{not} a controlled ablation of the decoding fix: it also differed in judge model, number of questions and memory leakage. We cite its numbers only to illustrate that these implementation details can dominate the result.

\subsection{Limitations}
\begin{itemize}
  \item \textbf{Sample size.} Five questions from one chapter; no confidence intervals were computed and none of the differences is statistically established.
  \item \textbf{Train/test overlap.} Some gold questions are in, or paraphrase, the training data (Section IV-E).
  \item \textbf{Single, same-family judge.} One LLM judge from the Qwen family, which may favour Qwen-based systems; no human evaluation or second judge.
  \item \textbf{Prompt mismatch.} The training system prompt (answer only from passages, or refuse) differs from the inference system prompt (short tutor answers), and the adapter was trained on a 4-bit base but run on a 32-bit base. Both may affect behaviour.
  \item \textbf{Hardware-dependent latency.} Latency was measured on one CPU-only machine; a GPU would change the local-model figures substantially.
  \item \textbf{Refusal behaviour not measured.} Although the dataset contains out-of-context refusal examples, we did not evaluate refusal accuracy.
\end{itemize}

%==============================================================
\section{Conclusion and Future Work}
We built a RAG tutor for operating systems that can use either a LoRA-fine-tuned 1.5B model running offline or a larger cloud model, and compared four configurations on five textbook questions. In this pilot the fine-tuned RAG system scored a mean faithfulness of 0.523 against 0.591 for the cloud RAG system, a difference too small to be conclusive, but it did so with an answer latency roughly twenty times higher on CPU. The main practical lessons concern evaluation hygiene: decoding penalties, conversation memory and judge quotas can each change the results more than model choice.

Future work, in priority order: (i)~a clean train/test split and the full 32-question bank with confidence intervals; (ii)~a second judge from a different model family and a small blind human evaluation; (iii)~stronger retrieval, since context precision is the weakest metric; (iv)~matching the training and inference prompts and checking earlier checkpoints for overfitting; (v)~measuring out-of-context refusal accuracy; and (vi)~GPU latency measurements.
